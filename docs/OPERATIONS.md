# Operations

How the VM deployment is run: deploy, upgrade, rollback, backup, access changes, certificates and incident checks. Each command below was run on the VM or the laptop between 2026-10-17 and 2026-10-20. A step that was not run is marked "not run", with what was done instead. Commands that were only planned are not listed.

The values used: VM `urumi-vm` (Azure Standard_B4ms, Ubuntu 24.04), k3s `v1.36.5+k3s1`, domain `vinayak-urum.me`, images `ghcr.io/vinayakjeet/<name>:<version>-<git sha>`, kubectl context `urumi-vm`.

## 1. Reach the cluster

The API port 6443 is closed in the Azure NSG. kubectl reaches it through an SSH tunnel to local port 16443.

```
make tunnel-up > /dev/null 2>&1 < /dev/null
kubectl --context urumi-vm get nodes
make tunnel-down
```

`tunnel-up` is safe to repeat. A dropped tunnel makes the next `make platform` fail before it applies anything; run `make tunnel-up` and repeat it (seen on 2026-10-19, the Helm revision did not move).

The check scripts refuse to run against the wrong cluster. To run them against the VM without changing the global kubectl context, use a private flattened kubeconfig:

```
(umask 077; kubectl config view --flatten --minify --context=urumi-vm > "$S/kc-vm")
export KUBECONFIG="$S/kc-vm" EXPECT_CONTEXT=urumi-vm
export APP=https://app.vinayak-urum.me MCP=https://mcp.vinayak-urum.me/mcp
```

`$S` is a private scratch directory. Delete the flattened file afterwards, because it holds the cluster credential.

## 2. Secrets

No secret is in the repository. Values reach pods only through Kubernetes Secrets.

| Secret                                              | Where it comes from                                                                                                                             |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| store MCP token                                     | `make store` writes it once to `deploy/secrets/store-<slug>-prod.yaml` (`openssl rand -hex 32`, mode 600). `make platform` reads the same file. |
| database, JWT, KEK, admin password                  | Generated by the platform chart on first install (`lookup`, so an upgrade keeps them).                                                          |
| `agent-llm` (`LLM_API_KEY`, `LLM_FALLBACK_API_KEY`) | Not chart-managed. Create it once, before `make platform`.                                                                                      |

```
kubectl --context urumi-vm create namespace platform
kubectl --context urumi-vm -n platform create secret generic agent-llm \
  --from-file=LLM_API_KEY=<(tr -d '\r\n' < deploy/secrets/llm-api-key) \
  --from-file=LLM_FALLBACK_API_KEY=<(tr -d '\r\n' < deploy/secrets/llm-fallback-api-key)
```

`LLM_API_KEY` is required. Without the Secret the agent pod does not start and `make platform` waits out its 15 minute timeout. Run `make platform` after the namespace exists; it applies the same namespace again without error. Replacing a key later: not run.

To read the admin password, run this in your own terminal. It prints the password:

```
kubectl --context urumi-vm -n platform get secret platform-bootstrap -o jsonpath='{.data.ADMIN_PASSWORD}' | base64 -d
```

k3s encrypts Secrets at rest in its datastore (`--secrets-encryption`). Check it on the VM:

```
ssh -i ~/.ssh/urumi-key.pem azureuser@20.193.153.146 'sudo k3s secrets-encrypt status'
```

It should say `Enabled`, with the same hash on every server. Checked on 2026-10-18, key `aescbckey` (AES-CBC, the k3s default).

## 3. First deploy, in order

Run once on 2026-10-17. Read the parts you skip, because later sections assume them.

1. k3s. The installer was downloaded to a file on the VM and its checksum steps were read first, then it was run with the version pinned:
   `sudo INSTALL_K3S_VERSION='v1.36.5+k3s1' sh /tmp/k3s-install.sh --secrets-encryption`.
   Traefik, kube-router (the NetworkPolicy controller), local-path storage and metrics-server stay on. The kubeconfig from `/etc/rancher/k3s/k3s.yaml` was copied to the laptop with the cluster, user and context renamed to `urumi-vm` and the server set to `https://127.0.0.1:16443`. The exact copy commands are not recorded.
2. Clock: `timedatectl` must say `System clock synchronized: yes`. OAuth tokens allow 30 s of skew. Right after a boot it said `no` and was `yes` 45 s later.
3. cert-manager, pinned to v1.21.2 (the newest minor that supports Kubernetes 1.36):
   ```
   kubectl --context urumi-vm create namespace cert-manager
   kubectl --context urumi-vm label namespace cert-manager pod-security.kubernetes.io/enforce=restricted
   helm --kube-context urumi-vm upgrade --install cert-manager jetstack/cert-manager \
     --version v1.21.2 -n cert-manager -f deploy/cert-manager/values.yaml --wait --timeout 5m
   kubectl --context urumi-vm apply -f deploy/cert-manager/cluster-issuers.yaml
   kubectl --context urumi-vm get clusterissuer
   ```
   Both issuers (`letsencrypt-staging`, `letsencrypt-prod`) must show `READY True`. They carry no ACME email.
4. The `agent-llm` Secret (section 2).
5. The store, then the platform. `IMAGE_TAG` is required for `ENV=prod`; the Makefile refuses to fall back to `dev`.
   ```
   make store ENV=prod SLUG=main NAME="Main Store" IMAGE_TAG=<version>-<sha>
   make platform ENV=prod SLUG=main IMAGE_TAG=<version>-<sha>
   ```
   Both run `helm upgrade --install ... --wait --rollback-on-failure --timeout 15m`. Never delete and recreate `main`: Let's Encrypt allows 5 certificates per week for the same host set.
6. Check:
   ```
   kubectl --context urumi-vm get pods -A | grep -v -E 'Running|Completed'
   kubectl --context urumi-vm get certificate -A
   curl -s -o /dev/null -w '%{http_code}\n' https://app.vinayak-urum.me/healthz
   curl -s -o /dev/null -w '%{http_code}\n' https://app.vinayak-urum.me/readyz
   ```
   The first command prints nothing when all is well. Both curls print 200. `/api/health` does not exist (404).

The first deploy used the staging issuer. Staging certificates are not trusted by Node, Inspector or Claude Code. The switch to production was a change of `ingress.tls.clusterIssuer` to `letsencrypt-prod` in both prod values files, then `make store` and `make platform` again. cert-manager reissued by itself when the Ingress annotation changed, so no `*-tls` Secret was deleted.

## 4. Release and upgrade

Images are built by GitHub Actions, not by `make` (`make images` refuses `ENV=prod`).

1. Tag and push (the user does this; the agent never pushes):
   `git tag v0.1.3 && git push origin v0.1.3`.
   The tag is the version. The workflow `.github/workflows/images.yml` builds all seven images as `<name>:0.1.3-<first 7 of the commit sha>`. A manual run takes the version as an input: `gh workflow run images.yml --ref main -f version=0.1.3`.
2. Wait for the run: `gh run list --workflow images.yml --limit 1`.
3. Check that each image is public and exists:
   `docker manifest inspect ghcr.io/vinayakjeet/<name>:<tag> > /dev/null && echo ok`, for gateway, control-plane, web, agent, woo-mcp, fx-mcp and store-wordpress.
4. Scan the pulled images for secrets before deploying. The script does not pull, so log out and pull first:
   ```
   docker logout ghcr.io
   docker pull ghcr.io/vinayakjeet/<name>:<tag>
   python3 -I scripts/image-secret-scan.py ghcr.io/vinayakjeet/<name>:<tag>
   ```
   Exit 0 is clean. For `store-wordpress`, exit 2 with exactly one hit, the test key blocks inside Debian's `libgnutls.so.30.40.3`, is the known false positive and counts as a pass. Any other file or any second hit is a finding: stop and read it.
5. Take the database dump (section 6) if the release touches a store.
6. Upgrade the platform release:
   `make platform ENV=prod SLUG=main IMAGE_TAG=<version>-<sha>`.
   Helm waits for readiness and rolls back by itself on failure (`--rollback-on-failure`). The control-plane's init container runs the migrations before the new gateway serves. Releases 0.1.2 (49 s) and 0.1.3 (62 s) both went through this way.
7. Check:
   ```
   curl -s https://app.vinayak-urum.me/api/config
   kubectl --context urumi-vm -n platform get pods
   ```
   The `version` field and the dashboard footer must show the new tag, and all eight platform pods must be `1/1`. Then run the live checks (section 9).

The `store-main` release was not upgraded in these runs (user ruling, 2026-10-19). B was the same code as A, so a store upgrade would restart WordPress and prove nothing more. Upgrading a store release: not run.

Provisioned stores take the store chart baked into the control-plane image and the tag of the platform release, so one tag must be used for all seven images.

Do not use `kubectl set env` on a chart-managed Deployment. The next `make platform` fails with a server-side apply conflict and Helm's own rollback fails too. Change settings through Helm values:
`make platform ENV=prod IMAGE_TAG=<tag> HELM_FLAGS="--wait --rollback-on-failure --timeout 15m --set agent.toolMode=search"`.
Repair after a stray `set env` (done once on k3d, not on the VM): add `--force-conflicts`.

## 5. Rollback

```
helm --kube-context urumi-vm history platform -n platform
helm --kube-context urumi-vm rollback platform <revision> -n platform --wait --timeout 10m
```

Run on 2026-10-19: from revision 4 (`0.1.2-4ce39e1`) back to revision 3 (`0.1.1-0f79236`). Helm recorded it as revision 5, "Rollback to 3", in 36 s. All eight pods were `1/1` on the old tag, `/api/config` and the footer showed the old version, and `e2e.sh` and `chat-check.sh` ended `OK`.

Rollback does not undo database migrations. Both releases in that run were on the same schema, so the run did not test a rollback across a migration. Migration 0002 adds a nullable column (`mcp_servers.tools_synced_at`) and fills it, so the old images run on it. A release with a destructive migration needs the dump from section 6 and a manual decision.

## 6. Backup and restore

The store database is MariaDB, a StatefulSet pod `mariadb-0`, database `wordpress`. The platform database is Postgres, a StatefulSet pod `postgres-0`, database `platform`, user `platform`. Both dumps are covered below.

Dump (run on 2026-10-19; the file holds customer data, so the directory is mode 700 and the file is never printed or committed):

```
install -d -m700 ~/backups/urumi
(umask 077; kubectl --context urumi-vm -n store-main exec mariadb-0 -- sh -c \
  'MYSQL_PWD="$MARIADB_ROOT_PASSWORD" mariadb-dump -uroot --single-transaction --routines wordpress' \
  > ~/backups/urumi/main-<date>.sql)
```

The root password is read inside the pod and does not appear on the command line. Check the file: the last line is `-- Dump completed`, the size is above 0, and `grep -c '^CREATE TABLE'` is above 0 (the live database had 46 tables on 2026-10-19).

Prove the dump by restoring it into a throwaway container of the same MariaDB version as the cluster (11.4.13 on that day; read the version from the StatefulSet image, do not assume it):

```
PW=$(openssl rand -hex 16); export PW
docker run -d --rm --name mdb-verify -e MARIADB_ROOT_PASSWORD="$PW" mariadb:11.4.13
docker exec -e MYSQL_PWD="$PW" mdb-verify mariadb -uroot -e 'CREATE DATABASE wordpress'
docker exec -i -e MYSQL_PWD="$PW" mdb-verify mariadb -uroot wordpress < ~/backups/urumi/main-<date>.sql
docker exec -e MYSQL_PWD="$PW" mdb-verify mariadb -uroot wordpress -e \
  'SELECT post_type, post_status, COUNT(*) FROM wp_posts GROUP BY post_type, post_status'
docker stop mdb-verify
```

Wait until `select 1` succeeds before the `CREATE DATABASE` (the run polled for up to 2 minutes). The counts matched the live database: 3 published products, 0 orders.

Restoring into the live store: not run. The proof is the restore into a throwaway container only. If it is ever needed, restore into a fresh `wordpress` database and check counts before switching anything. The WordPress files (uploads) live on the `wordpress` PVC and were not backed up either: not run.

### Platform database (Postgres)

Dump (run on 2026-10-22 against the VM, server 17.11, image `postgres:17-alpine`):

```
install -d -m700 ~/backups/urumi
(umask 077; kubectl --context urumi-vm -n platform exec postgres-0 -- sh -c \
  'PGPASSWORD="$POSTGRES_PASSWORD" pg_dump -h 127.0.0.1 -U platform -d platform --no-owner --no-privileges' \
  > ~/backups/urumi/platform-<date>.sql)
```

The password is read inside the pod from `POSTGRES_PASSWORD` (a Secret) and does not appear on the command line. Check the file: mode 600, size above 0 (198604 bytes), a line `-- PostgreSQL database dump complete` near the end, and `grep -c '^CREATE TABLE'` is above 0 (18 tables).

The dump holds user password hashes, API key hashes, OAuth token hashes, the audit log and the encrypted upstream credentials. Treat it like the store dump: directory 700, never printed or committed.

Encrypted credentials in the dump (`mcp_servers.auth_secret_enc`, `hosted_servers.secret_env_enc`) are useless without the key. The key (KEK) is in the Kubernetes Secret `platform-crypto`, key `KEK`, and is not in the dump. A restore into a new cluster also needs that Secret from the old cluster, or every stored upstream credential is unreadable and the servers must be registered again. The KEK was not backed up in these runs: not run.

Prove the dump by restoring it into a throwaway container of the same Postgres version as the cluster (read it with `show server_version` in the pod, do not assume it), then compare row counts per table on both sides with the same query:

```
PW=$(openssl rand -hex 16); export PW
docker run -d --rm --name pg-verify -e POSTGRES_PASSWORD="$PW" postgres:17.11-alpine
# wait until: docker exec pg-verify pg_isready -U postgres -h 127.0.0.1
docker exec pg-verify psql -U postgres -c 'CREATE DATABASE platform'
docker exec -i pg-verify psql -U postgres -d platform -v ON_ERROR_STOP=1 -q < ~/backups/urumi/platform-<date>.sql
docker exec -i pg-verify psql -U postgres -d platform -At < counts.sql
docker stop pg-verify
```

`counts.sql` lists every base table in `public` with its row count:

```
SELECT table_name || ' ' || (xpath('/row/c/text()', query_to_xml(
  format('select count(*) as c from %I.%I', table_schema, table_name), false, true, '')))[1]::text
FROM information_schema.tables WHERE table_schema='public' AND table_type='BASE TABLE' ORDER BY table_name;
```

Run the same file in the live pod (`kubectl exec -i postgres-0 -- sh -c 'PGPASSWORD="$POSTGRES_PASSWORD" psql -h 127.0.0.1 -U platform -d platform -At' < counts.sql`). Result on 2026-10-22: the restore exited 0, the live counts were the same before and after the dump, and `diff` of live against restored printed nothing, 17 tables. Examples: users 13, mcp_servers 3, audit_events 213, api_keys 65, stores 1. If the audit log is still growing while you compare, take the live counts right before and right after the dump and expect the restored counts to sit between them. The container was stopped (`--rm` removes it) and `docker ps -a` showed none left.

Restoring into the live platform database: not run. If it is ever needed, restore into a fresh database first, check counts, and only then point the control-plane and gateway at it.

When the dump is no longer needed, overwrite and remove it: `shred -u ~/backups/urumi/*.sql` (both the store and the platform dumps).

## 7. SSH and NSG source changes

Port 22 is open in the Azure NSG only to the operator's source addresses. When the operator's public IP changes, `ssh` and `make tunnel-up` end in `Connection timed out`, and the tunnel makes every kubectl command hang.

Find the current address and test the port:

```
curl -s https://api.ipify.org
timeout 8 bash -c 'echo > /dev/tcp/20.193.153.146/22'; echo $?
```

Then add that address to the source list of the SSH inbound rule on the NSG. The source list was widened twice (2026-10-18 to a /24, 2026-10-20 to add a second address), both by the operator outside this repository. No `az` command appears in the run history, so none is documented; the rule lives on the VM's NSG page in the Azure portal. After a change, run `make tunnel-up` again. The reasons and the exposure are in the SSH section of `docs/THREAT_MODEL.md`.

On the VM, sshd allows public keys only (`PasswordAuthentication` off, root login off), and fail2ban watches the `ssh.service` journal unit (on Ubuntu 24.04 the sshd records are under `ssh.service`, not `sshd.service`). Check the jail: `sudo fail2ban-client status sshd` over SSH.

## 8. Certificates

cert-manager requests one HTTP-01 certificate per host (`app.`, `mcp.`, and `<slug>.shop.` per store) through Traefik and renews it by itself. Let's Encrypt certificates last 90 days; the first ones were issued on 2026-10-17, and cert-manager renews 30 days before expiry by default, so the first renewal should fall around 2026-12-16. No renewal has happened yet, so the renewal path is untested here.

Check state and the issuer:

```
kubectl --context urumi-vm get certificate -A
echo | openssl s_client -connect app.vinayak-urum.me:443 -servername app.vinayak-urum.me 2>/dev/null | openssl x509 -noout -issuer -enddate
```

All certificates must be `READY True`, and the issuer must be Let's Encrypt without `(STAGING)`. A certificate stuck pending: read `kubectl --context urumi-vm describe challenge -A` before changing anything. Port 80 must reach Traefik for HTTP-01, and the solver pods need the `acme-solver-ingress` NetworkPolicy that both charts render when TLS is on.

## 9. Update the SSRF deny-list

The gateway and the control-plane refuse upstream URLs whose address is in `gateway.upstreamDenyAddresses` (checked at URL validation, at connect time and for OAuth client metadata fetches). `deploy/values-prod.yaml` lists the VM's public address as `/32`, so an admin cannot register the platform's own public endpoint as an upstream.

If the VM's public IP changes, change the list in the same step, or the new address is accepted as an upstream:

1. Edit `gateway.upstreamDenyAddresses` in `deploy/values-prod.yaml`.
2. Deploy with the current tag: `make platform ENV=prod SLUG=main IMAGE_TAG=<tag>`. Release 0.1.3 added this list and took 62 s.
3. Prove it: an admin `POST /api/servers` with `https://app.vinayak-urum.me/mcp` and with `https://<new ip>/mcp` must both answer 400 `url_rejected`. Done that way on 2026-10-20 for the then-current IP.

The Azure IP is Static (SKU Standard). Hosted servers in `mcp-hosted` are not covered by this list (`docs/THREAT_MODEL.md`, section 11).

## 10. Live checks and incident checks

Checks that end `OK` against the VM (run with the environment from section 1; `$S` is the scratch directory):

```
S=$S scripts/e2e.sh | tail -1            # 38 PASS on the VM
S=$S scripts/chat-check.sh | tail -1     # 8 PASS
S=$S scripts/oauth-check.sh | tail -1    # 29 passed, 0 skipped
S=$S scripts/obs-check.sh | tail -1      # 12 checks
scripts/netpol-check.sh platform
scripts/netpol-check.sh main
S=$S scripts/vap-check.sh
```

`oauth-check.sh` exits 3 and prints `INCOMPLETE` when its CIMD row is skipped. A skip is not a pass. `approvals-check.sh` needs a hosted server (a store cannot show approvals): `scripts/hosted-check.sh create pintest`, `SLUG=pintest S=$S scripts/approvals-check.sh`, `scripts/hosted-check.sh delete pintest`. `hosted-check.sh` needs `HOSTED_IMAGE=ghcr.io/vinayakjeet/fx-mcp:<tag>` on the VM, because the allowed image prefix refuses the local `fx-mcp:dev`. `stores-check.sh all` takes about 15 minutes and deletes the control-plane pod on purpose.

When something looks wrong, in this order:

1. Is the platform up? `curl` `/healthz` and `/readyz` (200 each), then `kubectl --context urumi-vm get pods -A | grep -v -E 'Running|Completed'`. A pod that is not `1/1` is the first thing to read: `kubectl --context urumi-vm -n platform logs deploy/<name> --tail=200`, for `gateway`, `control-plane` and `agent`.
2. Warnings in the logs: `kubectl --context urumi-vm -n platform logs deploy/gateway | grep -E '"level":(40|50)' | tail -5`. Log lines carry ids and outcomes, not arguments or tokens.
3. Is an upstream down? The Servers page shows the state and the last error kind for each server (dashboard, admin). The Health page shows rate, p50 and p95 per server. One dead upstream does not affect the others; its tools leave the list within about 30 s on every gateway replica.
4. Is the clock right? `timedatectl` on the VM. OAuth tokens fail beyond 30 s of skew.
5. Are certificates valid? Section 8.
6. Capacity: `kubectl --context urumi-vm top nodes` and `kubectl --context urumi-vm -n platform get pdb`. The Azure metric `CPU Credits Remaining` (Standard_B4ms is a burstable size) stayed flat at about 1.41k over 24 hours on 2026-10-19 across the replica, PDB and observability runs, so a falling balance is new.
7. Stores: `kubectl --context urumi-vm -n store-main get cronjob wp-cron` (a recent `lastSuccessfulTime`), and the Stores page for `Failed` stores with their reason. A failed store keeps its resources until its owner deletes it.
8. The daily audit retention job logs a line with a count: `kubectl --context urumi-vm -n platform logs deploy/control-plane | grep -i retention`.

A failed `stores-check.sh` leaves `check-one` and `check-two` stores: delete them with `scripts/stores-check.sh delete <slug>`. A failed `hosted-check.sh` leaves a hosted server `fx2`: delete it with `DELETE /api/hosted/<id>` (the id, not the slug, from the `hosted_servers` table).

Metrics and trace ids: `scripts/obs-check.sh` port-forwards to Prometheus and shows a `traceparent` sent through `https://mcp.vinayak-urum.me/mcp` in the gateway and woo-mcp logs.
